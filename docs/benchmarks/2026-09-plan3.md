# Plan 3 pooled-delivery validation and measurements

Recorded on 2026-09-11. The same-machine baseline used library commit
`b226a7f` with the API-neutral probe at `70767e5`; the after build used pooled
delivery commit `df16cef`. The probe source did not change between captures.
The earlier cross-machine numbers in [2026-09-plan2.md](2026-09-plan2.md) are
historical context and are not used for the before/after comparison here.

## Recording conditions

- Intel Core i7-13700H, 20 logical CPUs, Linux `7.0.0-31-generic` x86-64.
- GCC `15.2.0-16ubuntu1`, CMake 4.2.3, Release benchmark binaries.
- Measurements were pinned to CPUs 0–5 with builds and tests idle. CPU scaling
  and normal desktop activity remained enabled, so distributions are
  observations from this host rather than scheduling bounds.
- `sink_latency` sends exactly 10,000 snapshots at 1 kHz and includes the first
  snapshot; it does not warm the pool first. It stops the worker and drains
  before reporting.
- `rt_latency` uses 1,000 doubles split between a registered vector and scalar
  `LoggedValue`s, two transaction writers, 10 seconds at 1 kHz, and warms before
  its allocation counter starts.

## Delivery latency

Both runs delivered all 10,000 accepted snapshots. The pooled transport reduced
p50, p99 and p99.9 in this run. Its 2,275,919 ns maximum is worse than the
315,575 ns baseline maximum and is kept visible; one run does not establish its
cause or a universal tail-latency improvement.

The `T03_mcap_writer` example produced 1,500 messages in two channels and
`mcap doctor` exited zero, but it also emitted 497 global timestamp-inversion
notes in addition to the custom-profile note. Explicit producer tokens provide
FIFO order within each continuous channel/sink attachment; this example kept
both attachments stable. Removal and re-attachment replaces the token, so newer
work can be delivered before older records still queued from the prior
attachment, with no ordering guarantee across that boundary. The shared MPMC
queue also does not promise a global timestamp merge across channels. These are
observable file-order properties, not MCAP parse errors.

## Remaining scope

Plan 3 changes sink transport and lifecycle only. The channel still serializes
into its legacy temporary snapshot under its existing structure locks and then
copies payload/mask into a fixed 64-slot pool. Plan 4 retains channel epoch
publication, direct pooled serialization, payload/pool capacity setters,
strict oversize behavior, associated counters, and the complete reservation
contract. The independent simpler-design audit
recommends keeping the validated Plan 3 runtime and completing that smaller
remaining channel-side design; it is follow-up analysis, not an architecture
approval or a replacement for final review.
