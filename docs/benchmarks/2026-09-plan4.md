# Plan 4 final front-end validation and measurements

Recorded on 2026-09-11. The pre-change executable used the Plan 3 runtime at
`df16cef`; the final runtime is `16e812a`. Checkout `9d59fe2` contains only a
test-scheduling correction on top of that runtime.
The later final-fix wave changes portability guards, tests and allocation-report
output only; it does not alter the measured runtime or these values.

## Conditions and limits

- Intel Core i7-13700H, 20 logical CPUs, Linux `7.0.0-31-generic` x86-64,
  GCC 15.2.0 and CMake 4.2.3.
- Release project builds were used. Google Benchmark nevertheless reported
  that its library was built as Debug and that CPU scaling was enabled.
- The main matrix was unpinned on a shared desktop, with builds and tests idle
  but background load and CPU frequency uncontrolled. This differs from the
  pinned Plan 3 measurements and is observational data, not a scheduling bound.
- Each latency row except MCAP has 10,000 timed calls at 1 kHz after ten warm-up
  calls. MCAP has 60,000 timed calls. Allocation and failure totals cover timed
  calls; counters include warm-up.
- The 1,000-value workload is a 500-double raw vector plus 500 atomic
  `LoggedValue`s: 501 schema fields, an 8,004-byte initial payload and a 63-byte
  mask. The automatic reservation is 16,008 bytes per slot. With 64 slots,
  payload, mask and measured slot storage total approximately 1,040,832 bytes,
  excluding pool, link, schema and allocator overhead.

The measured path has no universal hard deadline. Custom serializers may
allocate or throw, non-strict variable payloads may grow a slot, and writer
critical sections plus normal desktop scheduling can extend latency.

## Same-machine Plan 3 versus final runtime

These are sequential but unpinned shared-desktop runs of the same transaction
workload. The earlier temporary logs disappeared; the before values below were
transcribed from their captured output into the Plan 4 validation record. All
six runs reported zero allocations per timed call and zero false returns. The
final runs also reported zero pool exhaustion, payload reallocations, oversize
drops and attachment drops.

| Sinks | Runtime | p50 (ns) | p99 (ns) | p99.9 (ns) | max (ns) | Blocking acquisitions | Max blocking wait (ns) |
|---:|---|---:|---:|---:|---:|---:|---:|
| 1 | Plan 3 `df16cef` | 24,319 | 524,284 | 2,508,627 | 3,512,655 | 5 | 28,006 |
| 1 | Final `16e812a` | 33,050 | 95,371 | 244,808 | 2,001,387 | 364 | 222,213 |
| 2 | Plan 3 `df16cef` | 32,108 | 1,038,743 | 3,757,125 | 3,771,643 | 5 | 2,830,188 |
| 2 | Final `16e812a` | 40,081 | 368,769 | 3,371,903 | 4,007,983 | 15 | 22,094 |
| 4 | Plan 3 `df16cef` | 36,347 | 215,837 | 3,007,795 | 3,146,751 | 95 | 254,035 |
| 4 | Final `16e812a` | 56,379 | 2,303,655 | 3,306,490 | 3,343,893 | 7 | 1,018,578 |

The final medians regressed in all three rows. Higher percentiles improved in
the one-sink row, were mixed in the two-sink row, and regressed in the four-sink
row. Maxima remain between 2.0 and 4.0 ms. The changing contention counts and
uncontrolled host load prevent attributing these differences to one mechanism.
The result demonstrates zero warmed allocations and successful delivery for
these runs, not a uniform latency speedup.

## Compressed MCAP soak

The default 64-slot pool absorbed the measured compression workload for 60
seconds with no pool exhaustion or publication failure. The harness drained and
closed the sink after the timed loop. The official `mcap` CLI reported 60,010
messages (60,000 timed plus ten warm-up), 613/613 zstd chunks, no overlapping
chunks and a 60.000897188 s duration. `mcap doctor` exited successfully with
only the expected note that `data_tamer` is not a well-known MCAP profile. A
separate file-order check found zero per-channel or global timestamp inversions
and zero container parse errors across all 60,010 records. It verifies MCAP
container parsing and record order; it does not decode payloads.

This run supports the 64-slot default for this workload. It is not proof that
64 slots cover every storage device, compression setting or retained-reference
pattern. A sink callback that retains 64 references can deliberately starve the
shared pool, causing every sink to miss later snapshots until a slot is released.

## Verification

The final test tree `340632c` passed the full suites sequentially. Debug
discovered 126 tests and passed 125; the other gates discovered 125 and passed
124. Debug completed in 6.17 s, ASAN+UBSAN with leak detection in 16.43 s,
TSAN in 18.47 s, Release in 5.28 s, and ROS in 11.82 s. Each gate had the same single privileged
priority-inheritance test skip because `CAP_SYS_NICE` was unavailable. Seven
additional ROS constructor/ABI tests also passed.

An earlier ROS run exposed a real test-scheduling assumption: the holder signaled
ready, slept for 500 µs, and the test assumed that the waiter had entered
`lock()` during that interval. The waiter could start later. Checkout `9d59fe2`
is a test-only repair: it updates the related transaction and mutex tests and
their shared helper to wait for an observable sleeping waiter on Linux and use
portable ownership checks. All sequential reruns passed; the production runtime
remains `16e812a`.

The leading missed simpler alternative from the
design audit is to
stop/join the worker, drain, then restart. It remains a deferred lifecycle
alternative; Plan 4 did not redesign the validated backend.

The final Debug gate also exposed an older sink-registry timing assumption:
its helper slept 1 ms before inspecting asynchronous delivery and observed only
2 of 10 queued snapshots under build load. Commit `340632c` replaces those
sleeps with an explicit drain through a test-only subclass. All three registry
tests passed 20 repetitions each, followed by the full gates above.

Final review also guarded Linux-only PI test code and limited `rt_latency` to
Linux builds. The host compiler exercised the non-Linux preprocessor path and a
Generic-system CMake check verified target selection; native macOS and Windows
builds were not run. These build, test and reporting changes preserve the
measured library runtime.

## Exact-allocation confirmation

After the final test repairs, checkout `340632c` ran the same 60-second,
1,000-value compressed-MCAP workload without writers, unpinned under
`SCHED_OTHER`, with no builds or tests running. The new integer counter reported
**0 allocations across 60,000 timed calls**. False returns, pool exhaustion,
payload growth, oversize drops, attachment drops and writer contention were all
zero. This confirms the exact total that the earlier rounded output could not
establish.

| Samples | p50 (ns) | p99 (ns) | p99.9 (ns) | max (ns) | Total allocations | False returns |
|---:|---:|---:|---:|---:|---:|---:|
| 60,000 | 47,290 | 170,525 | 259,686 | 1,825,891 | 0 | 0 |

Official MCAP `info` and `doctor` checks passed: 60,010 messages including
warm-up, 613 zstd chunks, no chunk overlap, and only the custom-profile note.
This additional diagnostic does not replace the original before/final matrix
or its recorded median regressions.
