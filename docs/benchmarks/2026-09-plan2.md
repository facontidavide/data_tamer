# Performance after Plan 2 — atomic values and write transactions

Recorded on 2026-09-11 at production commit `3812c2f`, following transaction
commit `f1cd33e`. Later review fixes change only tests, packaging and benchmark
tooling; the measured library implementation is unchanged. The historical baseline is [2026-09-baseline.md](2026-09-baseline.md),
measured at library commit `a851887`.

## Recording conditions

- Current machine: Intel Core i7-13700H, 20 logical CPUs, Linux `7.0.0-31-generic`.
- GCC `15.2.0-16ubuntu1`, CMake 4.2.3, system Google Benchmark 1.9.1;
  `release` preset (`-O3`, no sanitizers).
- All measurements pinned with `taskset -c 0-5`; five repetitions and
  `--benchmark_min_time=0.5s` for every microbenchmark. No builds or test suites
  ran during measurement. Background desktop activity remained; this is not an
  isolated real-time host. Load average at microbenchmark start was 6.16/3.31/2.09
  after preceding builds, falling to 1.31/2.34/1.94 by the end of the recording.
- CPU scaling remained enabled. The system benchmark library emits a DEBUG-build
  warning; the measured data_tamer library and executables are Release builds.
- **The historical baseline used an Ultra 7 265H, GCC 13.3, kernel 6.17 and
  Benchmark 1.8.3. These side-by-side numbers are not a controlled speedup
  comparison.** A same-machine baseline rerun is needed to quantify improvement.
- Each latency case measures 10,000 calls at 1 kHz after 10 warm-up calls.
  Counters are cumulative and include warm-up; allocation counts cover measured
  snapshot-thread calls only. The hook counts C++ `new`/`delete`, not direct
  `malloc` inside moodycamel.

Every run returned `true` for all 10,000 measured snapshots. The two transaction
writers caused 268 blocking acquisitions and a 74,188 ns maximum blocking wait;
serialization is excluded from that wait counter. The observed transaction
snapshot maximum was 196,361 ns, below the 1 ms sampling period in this run;
this is an observation, not a worst-case scheduling bound.

`--vector-writer` adds one `LoggedValue<std::vector<double>>` to the baseline
1,000 scalar elements, with an independent writer cycling its length from 1
to 64 every 200 µs. `--transactions` instead wraps each existing scalar writer's
batch of updates. The FIFO attempt reports `CAP_SYS_NICE` unavailable and runs
as `SCHED_OTHER`; it is not evidence of real-time priority-inheritance bounds.

## Correctness validation

- Debug, ASAN+UBSAN (including leak detection) and TSAN: 88 tests each,
  87 passed and the privileged PI test skipped. Release: 89 tests, 88 passed
  and the same skip, including the invalid-CLI regression. No compiler or
  sanitizer diagnostics. ASAN ran outside the traced sandbox because LeakSanitizer cannot
  operate under ptrace; sanitizer settings and leak detection were preserved.
- ROS Lyrical: both source files and both sink ABI assertions compiled; six
  existing ROS publisher constructor tests and the ABI test passed at runtime
  with localhost DDS. The local message package was built with colcon, and
  CMake used `-DMCAP_LIBRARY=/opt/ros/lyrical/lib/libmcap.so`. This installation
  lacks the old gtest vendor package, so the ROS tests were compiled and linked
  explicitly using the configured target flags and libraries.
- `T03_mcap_writer` produced 1,500 messages on two channels. The compressed
  latency run produced 10,010 messages (including warm-up). Both passed the
  official `~/Apps/mcap-linux-amd64 doctor` with exit 0; its only note was that
  `data_tamer` is a custom rather than well-known profile.
